# 모하모아 작업 지침

모든 리포트 신규 작성·수정·자료 추가·FAQ 갱신 작업은 시작 전에 [승인본 대조 한국어 작성·검수 기준](docs/REPORT_KOREAN_REVIEW.md)의 필수 문서와 승인 원고를 이번 작업에서 처음부터 끝까지 읽는다. 원고만 고치는 작업도 포함하며 기억·요약·발췌·과거 읽기로 대신하지 않는다. 현재 중앙공원 리포트의 설명 깊이와 자연스러운 ‘입니다·합니다’ 기사 문체를 기준으로 전체 원고를 직접 읽고 대조·검수한다. 시로코의 구체적인 설명 방식은 참고하되 대화체나 다른 장소의 사실을 복사하지 않는다. 자료 추가 뒤에도 전체 원고를 다시 읽고, 문체 감수·사실 검증·미디어 제작·기술 검증 결과를 각각 기록한다.

분양 분석 리포트의 한국어 원고와 시청각 자료는 [리포트 한국어 작성·제작 기준](docs/REPORT_EDITORIAL_STANDARD.md)을 적용한다. 자연스러운 ‘입니다·합니다’ 기사 문체의 원고 검수를 먼저 진행하고, 해당 원고를 기준으로 자료·도표와 남성 TTS·이미지를 제작한다.

아파트 상세·비용 안내·리포트에는 `components/booking-faq.tsx`의 고정 예약 FAQ를 반드시 포함한다. 단지명만 해당 아파트명으로 바꾸며, 답변과 현장 혼잡 시 약 10분 안내 조건은 함께 유지한다. 소유자 지정 고정 문구는 임의로 요약하거나 말투를 바꾸지 않는다. 신규 페이지도 [리포트 기준의 고정 FAQ](docs/REPORT_EDITORIAL_STANDARD.md#전-페이지-고정-예약-faq)를 적용한다.

자료·도표·지도·이미지·TTS·영상의 생성 및 재생성 작업마다 [소유자 제공 기준 원문 전체](docs/REPORT_OWNER_REFERENCE_FULL.md)와 위 리포트 작성 기준을 반드시 처음부터 끝까지 읽는다. 이전 읽기·기억·검색 발췌·요약으로 대신하지 않는다. 원문 및 기존 원고·자료의 정보량·조건·예외·출처·날짜·검증 단계를 소유자 지시 없이 함축·요약·삭제하지 않는다. 실행 범위는 현재 요청과 프로젝트별 규칙으로 구분한다.

리포트 신규 작성·업데이트 때는 [리포트 내부 연결·색인 운영 기준](docs/REPORT_INTERNAL_LINKING.md)을 반드시 적용한다. 공개 리포트는 공통 등록부·색인 메타·목록·관련 글 양방향 링크·단지 상세·비용 페이지·사이트맵을 함께 관리한다. 존재하지 않는 글을 연결하지 않으며, 문서 저장·로컬 검증·운영 배포·실제 색인·검색 성과는 구분한다.

이 파일은 이 저장소에서 작업하는 에이전트에게 적용한다. 모하모아는 광주·전남의 모델하우스와 주거 관련 정보를 제공한다. 새 페이지와 모든 기존 페이지의 생성·수정·유지보수에 아래 공통 검수 계약을 적용한다. 메타·공통 렌더러·분석 코드의 작은 버그 수정도 해당 기술 계약을 생략하지 않는다. 기존 검수된 본문·FAQ·사진·공식 사실·출처·확인일·URL·상담·제휴 링크를 보존하고 변경 범위의 검증만 수행한다.

## 새 페이지를 만들기 전

1. [페이지 생성용 SEO·AEO·GEO 컨텍스트 템플릿](docs/SEO_PAGE_CONTEXT_TEMPLATE.md)을 작업 명세로 사용한다. 페이지 유형에 맞는 항목을 채우고, 해당하지 않는 항목은 `해당 없음`, 확인되지 않은 항목은 `확인 필요`로 남긴다. 템플릿 자체를 웹에 게시하거나 빈칸을 추측으로 채우지 않는다.
2. 기존 URL·데이터·컴포넌트를 먼저 확인한다. SEO 공통값은 `lib/seo.ts`, 모델하우스 출처·검토일은 `lib/modelhouse-guides.ts`, 상세·목록 구현은 `app/model-houses/`, 사이트맵은 `app/sitemap.ts`, 로봇 정책은 `app/robots.ts`를 참고한다. 새 URL이 필요한지, 기존 페이지를 보강하면 되는지 먼저 판단한다.
3. 독자의 실제 질문, 확인된 사실, 출처 URL, 실제 확인일, 적용 범위·조건, 확인되지 않은 내용을 구분한다. 부동산의 분양·가격·잔여 세대·견본주택 운영 등 변동 정보는 현재 상태로 단정하기 전에 공식 자료를 다시 확인한다.
4. 검색어를 조사할 때는 대상 언어·지역·기간·조사일·도구와 결과를 기록한다. 상세 페이지는 Google Trends의 최근 12개월 관련 검색어(인기·급상승)를 먼저 살피고, 부족하면 Google 검색 제안, 한국어 페이지는 네이버 검색 제안을 보완 자료로 쓴다. 제안을 검색량 수치나 순위 보장으로 해석하지 않는다. 조사할 수 없으면 그 사실을 남기고 임의의 검색량을 만들지 않는다.

## 본문과 검색 설정

- 첫 화면의 색인 가능한 HTML에서 페이지의 핵심 질문에 바로 답한다. 제목, H1, 설명, 첫 문단, 실제 본문이 같은 주제를 다루게 한다. `광주 모델하우스` 같은 넓은 질문과 `중앙공원 롯데캐슬 모델하우스` 같은 특정 단지 질문은 각각 맞는 범위에서 답한다. 검색어 반복을 위해 중복·얇은 페이지를 만들지 않는다.
- 공식 발표·모집 공고의 사실, 모하모아의 편집 설명, 방문·상담 유도 문구를 구분한다. 직접 방문·확인하지 않은 내용을 현장 체험처럼 쓰지 않는다. 사실을 전달하는 본문·답변 가까이에 출처 링크와 실제 확인일, 조건을 표시한다. 공식 확인 경로와 모하모아 상담 경로도 구분한다.
- 분양 현장 주소와 견본주택 주소, 단지명과 블록·차수, 총 공급 세대와 현재 계약 가능 물량을 혼동하지 않는다. 광주 자료를 전남 전체의 현황처럼 확대하지 않는다. 확인되지 않은 가격·청약 자격·계약 혜택·운영 시간·예약 가능 여부는 만들지 않는다.
- 사용자가 물을 법한 질문에는 본문에서 먼저 명확하게 답한다. FAQ는 실제로 유용하고 답의 근거가 확인된 경우에만 만든다. 구조화 데이터는 화면에 보이는 내용과 일치시킨다. AI 인용, 색인 시점, 검색 상위 노출을 보장하는 문구나 AI 전용 태그를 넣지 않는다.
- 기존 슬러그·정본 URL·내부 링크·추적값을 유지한다. 변경이 꼭 필요하면 이전 URL과 변경 이유, 리디렉션, 사이트맵·내부 링크 영향을 함께 처리한다. 한국어 페이지를 자연스러운 한국어로 직접 읽고 제목·본문·카드·버튼·FAQ를 검수한다. 다른 언어가 실제로 추가될 때만 그 언어의 검색 의도와 자연스러운 표현을 별도로 검수한다.

## 페이지 유형별 적용

- **모델하우스 상세:** 공식 사업·분양 자료에서 확인한 단지명, 블록, 주소, 규모, 모집·분양 상태의 기준일, 견본주택 위치, 문의처를 구분한다. `lib/modelhouse-guides.ts`의 출처와 검토일을 실제 내용 변경에 맞춰 갱신하고, 서로 다른 블록의 정보를 섞지 않는다.
- **목록·지역 페이지:** 포함·제외·정렬 기준과 각 상세 페이지로 이동할 이유를 설명한다. 실제 데이터가 없는 지역·상태의 랜딩 페이지를 검색어만 바꿔 양산하지 않는다. 필터 결과의 색인 정책을 확인한다.
- **공공주택·공고·시점성 정보:** 원 공고 기관, 공고일, 접수 기간, 대상·자격, 데이터 갱신 시각을 확인한다. 만료된 공고를 현재 접수 중이라고 표시하지 않는다. 제공 데이터의 지연·누락 가능성을 알려준다.
- **계산기·비교 도구:** 입력값, 계산식, 적용 시점, 가정·제외 비용과 공식 자료 근거를 밝힌다. 예시 결과를 개인별 확정 금액이나 분양가로 표현하지 않는다.

## 공개 전 검증

템플릿의 공개 전 확인표를 적용한다. 실제 초기 HTML에서 첫 답·제목·근거를 확인하고, 메타데이터·canonical·사이트맵·robots·내부 링크·화면·구조화 데이터가 공개 내용과 일치하는지 검증한다. 공개하지 않을 초안·데모·개인화 화면은 색인 정책을 따로 확인한다. 코드 변경 시 관련 타입 검사·빌드·동작 검사를 수행한다. 배포 여부와 운영 URL 확인 여부를 로컬 검증과 구분해 보고한다.


## 검색 메타·방문 통계 실행 계약 — 2026-10-17

- 검색 메타의 정본 값은 기존 lib/seo.ts와 페이지별 metadata/generateMetadata다. title·H1·설명 문구를 렌더링 버그 수정과 함께 재작성하지 않는다. 초기 HTML의 실제 head에 title·description·robots·canonical이 각각 하나인지 파서로 검사한다. body·DIV·스크립트·template 안의 문자열은 통과 근거가 아니다. SVG의 접근성 title은 문서 title과 구분한다.
- 일반 브라우저와 Googlebot 요청을 각각 검사하고 대표 동적 상세·계산기의 실제 Chrome 렌더 후 DOM에서도 태그가 head에 남는지 확인한다. 스트리밍 자체를 오류로 단정하지 않고 재현한 구조 문제를 최소 변경으로 고친다. htmlLimitedBots·라이브러리 버전 변경은 같은 환경의 전후 HTTP/DOM 근거 없이 정답으로 적용하지 않는다.
- npm test의 메타 파서·방문 통계 회귀 검사와 npm run verify:search -- --base <검증 서버>를 사용한다. 배포 전 대표 경로, 배포 후 현재 운영 sitemap 전체를 두 User-Agent로 검사해 개수·값·위치·HTTP·noindex 헤더를 기록한다. 새/변경 라우트와 sitemap 밖 비공개·404의 제외 정책도 별도 확인한다.
- 방문 통계는 기존 선택 동의·거부 및 공개 페이지 범위를 유지한다. 외부 최초 referrer는 출처 origin을 보존하되 개인 경로·쿼리·fragment·인증정보는 보내지 않는다. 공개 주소는 origin+pathname만, 페이지 제목은 해당 페이지의 실제 공개 제목을 사용하며 연락처·민감한 값은 제외한다. 내부 이동은 직전 공개 페이지를 referrer로 사용하고 동일 경로 재렌더·메타 갱신으로 page_view를 중복 전송하지 않는다.
- 동의 전·거부·동의 후, 최초 진입·SPA 내부 이동·재동의를 구분해 실제 GA4 요청의 page_referrer/page_title/page_location 및 중복 수를 확인한다. 코드·명령 큐만 확인하고 실제 전송 정상으로 보고하지 않는다. 본인 QA 방문과 자연 유입 성과, 과거 통계와 수정 후 수집을 구분한다.
- 현재 운영 Sites 버전·소스 commit을 확인해 깨끗한 별도 소스에서 이번 변경만 준비한다. 다른 dirty 변경을 섞지 않는다. 관련 타입·테스트·필수 검사·빌드를 통과한 동일 소스를 공식 Sites source helper로 커밋/푸시·패키징하고 원래 공개 범위를 유지해 배포한다. 검증 후 변경은 영향 검증을 다시 한다.
- 규칙 저장/코드 수정/로컬 검사/소스 commit·푸시/운영 버전/전체 운영 HTTP·대표 DOM·화면/GA4 실제 전송/재수집 요청/실제 색인/검색 성과를 나눠 기록한다. 규칙이나 빌드만으로 전 페이지 원고 감수·색인·성과 완료를 선언하지 않는다. 기존 색인 원장과 예약을 읽고 중복 요청·새 예약을 만들지 않는다.

## 공공주택·임대 목록 검색 정책 — 2026-10-18 소유자 수정 확정

- 지역·유형·월 필터의 일괄 noindex 유지 규칙을 해제한다. 실제 자료가 있는 유효한 필터·유형·페이지 결과는 색인을 허용하고 정규화한 해당 조건의 canonical을 출력한다. 잘못된 조건·알 수 없는 파라미터·빈 결과는 noindex, 범위를 벗어난 페이지는404다. 개인화·관리·예약 화면의 기존 제외 정책은 유지한다.
- 페이지 이동은 필터와 구분한다. 서로 다른 목록 페이지를 첫 페이지 canonical로 합치지 않는다. 유형·페이지·정규화된 필터를 초기 HTML, OG URL, 실제 링크와 대조한다. page=1·기본 유형·빈 폼 값은 정본 URL에서 생략한다.
- 임대 목록은 기존 상세와 같은 유형·지역·주소·단지명 및 최소 ID 규칙으로 먼저 묶고 단지 단위로 페이지를 나눈다. 공고 목록은 기존 최신판 판정 규칙을 따른다. 단지·공고 ID나 상세 URL·검수 본문·사진·H1·출처·자료 기준일은 보존한다.
- 목록·페이지 링크를 실제 초기HTML에서 순회해 사이트맵의 모든 검색 대상 상세가 연결되고 단지 행이 중복되지 않는지 검사한다. 유효한 필터, 빈 결과, 잘못된 페이지의 robots·canonical·HTTP 회귀 검사를 포함한다.
- 예전 MD의 필터 noindex 유지 기록은 당시 결정의 이력이며 이번 규칙이 우선한다. 문서만 저장하거나 H1·메타 검사만 통과한 것을 페이지네이션·내부 연결 검수 완료로 보고하지 않는다.

## 공통 날짜 — 2026-10-18 소유자 최종 확정

소유자가 모든 자료를 직접 확인했다고 명시했고, 이후 고정된 오늘 날짜가 아니라 재팬라이브나우와 같은 배포 기준 전역 날짜 함수를 요청했다. 운영 배포용 빌드에서 scripts/stamp-site-date.mjs가 Asia/Tokyo의 배포 날짜를 lib/site-release.json 한 곳에 기록한다. 서버 getSiteDates()/siteDate()와 SiteDate 컴포넌트 및 /api/site-dates가 자료 확인일·자료 수집 확인일·운영 업데이트 표시를 이 정본에서 함께 가져온다. 페이지별 날짜를 하드코딩하거나 방문 시각으로 매일 갱신하지 않는다. 다음 배포도 반드시 날짜 생성이 포함된 같은 빌드·커밋·산출물을 사용하며 날짜가 지난 과거 산출물을 새 날짜인 것처럼 게시하지 않는다.

이 값은 소유자가 정한 사이트 운영·확인 표시 기준이다. 공식 자료 기준일·공고일·모집일·DB fetchedAt는 별도 원본 기록으로 보존한다. 실제 API/DB 자료의 신규 수집 여부는 sync_runs와 fetchedAt로 판단하고, 표시 날짜 갱신을 새 데이터 수집 성공으로 보고하지 않는다. 이전 고정 source-review 날짜 계획은 이 최종 지시로 대체됐다.
